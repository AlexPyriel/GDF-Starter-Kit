# Код-стандарт: Документирование

## Обязательность
- Документация обязательна для всех публичных элементов системы: классов, интерфейсов, DTO, свойств, перечислений и `ScriptableObject`-конфигов.
- Использовать XML documentation: `<summary>`, `<param>`, `<returns>`, `<value>`.
- Формулировки должны быть краткими и понятными, объяснять назначение элемента, а не дублировать его имя.
- Язык документации:
    - Для этого проекта использовать английский язык.
    - Для новых проектов без зафиксированного требования сначала уточнять предпочтительный язык у заказчика.
    - Если заказчик настаивает на английском, писать на английском.
    - Иначе писать на русском.
- Для публичных реализаций интерфейсов и наследников публичных базовых членов предпочитается использовать `<inheritdoc />` вместо дублирования XML-комментариев.
- Если реализация требует дополнительного пояснения сверх контракта, рядом с `<inheritdoc />` или вместо него добавлять явную XML-документацию.

## Классы
- Если класс **не реализует интерфейс**, `summary` обязателен.
- Если класс **реализует интерфейс**, отдельный `summary` можно опустить, но рекомендуется добавить при особой роли реализации.
- Для публичных методов и свойств реализации предпочитается `<inheritdoc />`, если контракт уже полноценно описан на интерфейсе или в базовом классе.

## DTO
- Каждый DTO-класс должен иметь `summary` с назначением.
- Каждое публичное свойство DTO должно иметь XML-комментарий с описанием значения.

## Интерфейсы
- Все архитектурные интерфейсы (сервисы, репозитории, менеджеры и т.п.) должны иметь `summary` с описанием роли в системе.
- Методы интерфейсов документировать с использованием `summary` + `param` + `returns`.

## Enum
- Каждый `enum` должен иметь `summary` с назначением.
- Каждое значение `enum` должно быть документировано отдельным `summary`.

## ScriptableObject-конфиги (Unity)
- Каждый `ScriptableObject`-конфиг должен иметь `summary` с назначением и областью применения.
- Все публичные поля конфига должны иметь комментарии, поясняющие смысл и влияние.
- Для editor-используемых конфигов формулировки должны быть понятны не только программистам, но и гейм-дизайнерам.

## Рекомендации по качеству комментариев
- Комментарии должны объяснять **зачем** существует элемент, а не просто **что** он делает.
- Избегать пустого дублирования имени.
    - Плохо: `/// <summary>Метод Authenticate</summary>`
    - Хорошо: `/// <summary>Выполняет аутентификацию пользователя по логину и паролю.</summary>`

## Definition of Done (документация)
- При создании или изменении публичных элементов документация обновляется обязательно.
- Без XML-документации или корректного `<inheritdoc />` для новых публичных классов, интерфейсов, методов, DTO, `enum` и `ScriptableObject`-конфигов задача не считается завершённой.

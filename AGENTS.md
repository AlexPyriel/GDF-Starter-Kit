# AGENTS.md

Локальные инструкции для AI-агента в этом репозитории (Unity проект).

## MCP и инструменты

- Для задач поиска по коду, анализа классов, методов, ссылок, зависимостей и точечных изменений сначала использовать Serena MCP, если он доступен.
- Не ждать отдельной просьбы пользователя для использования Serena, если задача по смыслу требует семантического анализа кода.
- Предпочитать семантический поиск через Serena вместо чтения больших файлов целиком, когда это ускоряет работу и снижает расход контекста.
- MCP-серверы запускать только когда они реально нужны для текущей задачи.
- Не перезапускать и не останавливать MCP-серверы между мелкими шагами без необходимости.
- Если MCP-сервер был поднят для текущей задачи и после её завершения больше не нужен, агент должен завершить его, если сервер не управляется жизненным циклом клиента автоматически.
- О запуске и остановке MCP-серверов агент должен явно сообщать пользователю.
- Для обычного поиска по файловой системе использовать быстрые локальные инструменты, такие как `rg` и `fd`, и не заменять ими Serena там, где нужен поиск по символам и ссылкам.
- Для задач, требующих доступа к Unity Editor, сцене, GameObject, компонентам, AssetDatabase, Console, play mode, selection или editor automation, сначала пытаться использовать UnityMCP, если он доступен.
- Если UnityMCP не подключается или Unity-side недоступен, явно попросить пользователя открыть нужный Unity-проект, дождаться завершения компиляции и убедиться, что в проекте установлен и активен `MCP for Unity`.
- Не использовать UnityMCP там, где задача решается локальным анализом файлов репозитория без обращения к Unity Editor.
- При работе с git использовать локальный CLI `git` и не выполнять разрушительные команды без явного подтверждения пользователя.
- Если для задачи нужны merge request, pipeline, issues или review metadata в GitLab, можно использовать `glab`, если он установлен.

## Регламент работы

- На каждый вопрос/запрос сначала найти целевые файлы и понять контекст.
- Если задача сформулирована расплывчато, предложить несколько конкретных вариантов выполнения и кратко обозначить отличия между ними.
- Если есть неоднозначность, спросить пользователя.
- Работать по задачам последовательно, без перескоков между пунктами.
- Если задача требует нескольких логически отдельных блоков изменений, сначала разбить её на подзадачи.
- Подзадача — это логически завершённый блок изменений, а не отдельная команда.
- Read-only шаги (поиск, просмотр файлов, сбор контекста) можно выполнять без отдельного подтверждения на каждый микрошаг.
- Перед каждой подзадачей с изменениями сначала:
    1. Кратко описать, что будет сделано и как.
    2. Если есть несколько осмысленных вариантов, кратко перечислить их, указать рекомендуемый и попросить выбор или подтверждение.
    3. Если вариант один, показать план подзадачи и завершить запрос строкой: `Жду подтверждения.`
    4. Отправить запрос подтверждения только один раз.
    4.1. Не дублировать блок подтверждения, не повторять план подзадачи и не копировать один и тот же текст дважды в одном ответе.
    4.2. После подтверждения пользователя не цитировать заново весь ранее отправленный план, если пользователь не попросил повторить его явно.
    5. После подтверждения внести изменения.
    6. Кратко подвести итог по подзадаче и перейти к следующей.
- Не вносить неоговоренные архитектурные усложнения и "заделы", если они не требуются текущим пунктом ТЗ.
- НИКОГДА НЕ ПИСАТЬ ВРЕМЕННЫЕ КОМПРОМИССЫ, ЕСЛИ С ПОЛЬЗОВАТЕЛЕМ УЖЕ СОГЛАСОВАН НОРМАЛЬНЫЙ ПЛАН РЕАЛИЗАЦИИ. В ТАКОЙ СИТУАЦИИ СРАЗУ ДЕЛАТЬ КАК НАДО ПО СОГЛАСОВАННОЙ АРХИТЕКТУРЕ, А НЕ ЧЕРЕЗ ВРЕМЕННЫЕ УПРОЩЕНИЯ.
- При спорных местах сначала фиксировать интерпретацию и получать подтверждение до реализации.
- Все публичные изменения сопровождать кратким объяснением "что/почему" и ссылками на измененные файлы.
- Ссылки на файлы в ответах всегда оформлять только в формате `[ИмяФайла.cs](file:///absolute/path)`. Любой другой формат ссылки на файл считать неправильным.
- Никогда не использовать ссылки на файлы в виде `/absolute/path`, `./relative/path`, `Assets/...`, markdown-ссылки без `file:///`, или любые другие варианты, даже если они выглядят валидными.
- В `file:///absolute/path` обязательно использовать URL-encoding для пробелов и символов `[` `]`.
- Считать рабочим только формат, который открывается в Rider из окна чата: markdown-ссылка с `file:///` и URL-encoded absolute path.
- Если нужно указать место в файле, номер строки писать обычным текстом рядом со ссылкой, не использовать якоря вида `#L123`.
- Делать точечные правки, не "рефакторить по пути" без запроса.
- Пока подтверждение не получено и действие не выполнено, отвечать только промежуточным сообщением, не использовать `final`.
- `final` использовать только после завершения подзадачи или всей задачи.
- Не подменять обычное подтверждение искусственным выбором вариантов, если реального выбора нет.
- После правок кратко перечислить, что изменено и где.
- После выполнения задачи предложить готовый commit message по Conventional Commits (subject + при необходимости body).

## Общие правила

- Работать аккуратно и минимальными изменениями.
- Сначала находить целевые файлы и собирать контекст, затем предлагать или выполнять изменения.
- Не трогать автогенерируемые файлы без необходимости (`Library/`, `Temp/`, `obj/`, `Logs/`).
- Не переименовывать папки/ассеты Unity без явной причины (чтобы не ломать `.meta` связи).
- При изменении файлов в `Assets/` сохранять существующую структуру проекта.
- При создании новых файлов/папок убедиться, что соответствующие `.meta` файлы созданы и не потеряны при операциях (особенно при перемещении через терминал).

## Что обычно можно менять

- `Assets/**` (скрипты, сцены, префабы, ScriptableObject и т.п.)
- `Packages/manifest.json` и related package config (если задача требует)
- `ProjectSettings/**` (только если это часть задачи)

## Что лучше не менять без запроса

- `Library/**`
- `Temp/**`
- `obj/**`
- `Logs/**`
- `.csproj` и `.sln` (если пользователь не просил)

## Unity-специфика

- Учитывать сериализацию Unity (`[SerializeField]`, публичные поля, совместимость с инспектором).
- Не ломать ссылки в сценах/префабах резкой сменой имён классов/namespace.
- Если добавляется новый `MonoBehaviour`/`ScriptableObject`, следить за именем файла и класса (должны совпадать).
- При создании новых классов или добавлении зависимостей проверять наличие `Assembly Definition` (`.asmdef`) в текущей или родительских папках и обновлять их при необходимости.
- Использовать `SerializedDictionary` (из пакета AYellowpaper) вместо обычного `Dictionary` для полей, которые должны отображаться в инспекторе Unity.

## Проверка

- Если возможно, запускать только безопасные локальные проверки.
- При отсутствии доступа к Unity Editor проверять отсутствие ошибок компиляции (`error CS...`) через поиск по тексту в логах или используя команду `grep -r "error CS" .` (с учетом исключений Library/obj).
- Не запускать тяжёлые/долгие операции Unity Editor без явного запроса.
